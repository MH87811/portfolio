About

Written plainly

I build backend systems with a focus on reliability, architecture and understanding how software works beneath the surface.

Background

My first web applications were written in PHP with Laravel. That is where I learned the shape of a request: routes, controllers, a database behind them. I moved to Python with Django and Django REST Framework, and later to Go. Each change taught me to ask a sharper question about the tool I had left. What was the framework doing for me, and what did I not know?

I work mostly on APIs, authentication and real-time services. I write these projects up the way I would want to read them: problem first, trade-offs visible, dead ends included.

Technical interests

Authentication and session security. Concurrency in Go. How an HTTP request turns into bytes on a wire. What a database does with a query once the table is large. WebSockets and the failure modes of long-lived connections.

I am most interested in places where an abstraction leaks, because that is where understanding pays off.

Engineering philosophy

Software is a set of decisions, and most bugs are decisions nobody recorded. I prefer systems that fail in predictable ways over systems that are fast and surprising.

  • Reliability before features.A feature is only as good as the worst day it has to survive.
  • Read the layer below.Use the framework, and know what it does when it is called.
  • Write it down.A decision that is not recorded gets made again, usually worse.

Current direction

I am deepening networking and testing, and learning to reason about whole systems instead of single services. The next projects are larger: a service split across several nodes, with observability from the first commit.

I am looking for backend roles and collaborations where code is reviewed carefully and reliability is a shared concern.

Why it matters

Testing

Why it matters

Tests are how a service stays changeable. I want the habit of writing the failing test first, and the judgment to know which tests deserve to stay: handlers against a real database, pure logic in table-driven cases.

In practice

Unfinished work, short notes and small experiments. Entries are added as I learn, and some of them grow into projects.

2026-10-04 ExperimentHow many goroutines does a WebSocket connection need? In progress

PULSE runs a reader and a writer goroutine for every connection. This experiment compares that layout with a shared pool of writers. The question is whether the extra goroutines cost anything measurable at ten thousand idle sockets, or whether I am optimizing a number that never mattered.

Results will go here together with the load client and the raw numbers.

2026-09-27 NoteRefresh token reuse, in plain words Published

A refresh token is a one-time ticket. If a ticket that was already used shows up a second time, either the owner is confused or someone copied it. The server cannot tell which, so it cancels the whole family of tickets and asks for a new login.

The cost is one annoyed user. The alternative is a quiet intruder.

2026-09-19 LogWatching a TCP handshake Ongoing

One command and one request to a local server are enough to see the start of a connection.

The output shows the SYN and the SYN-ACK. Drop the flag filter to see the final ACK and the HTTP request that follows. Seeing the handshake once makes later timeout bugs easier to read.

2026-09-08 ExperimentTable-driven tests for Gin handlers Published

One slice of cases, each with a method, path, body and expected status, driven through httptest. Adding a case costs three lines. The first version reported every failure with one generic message, so each case now runs as its own subtest.

2026-08-30 NoteRight-to-left layout with logical properties Published

Replacing margin-left with margin-inline-start removed most of the right-to-left overrides from the old portfolio stylesheet. The overrides that remained were icons and arrows, which have to be mirrored on purpose.
